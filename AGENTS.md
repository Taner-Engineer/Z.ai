# Глобальная память ZCode

Эти правила применяются во всех проектах на любой машине. Файл синхронизируется
через репозиторий Z.ai — отредактировали здесь, сделали commit + push, на другой
машине запустили `update.sh` / `update.ps1`.

## Язык и общение

- Отвечай по-русски.
- Отвечай кратко и по делу, без воды.

## Предпочтения по коду

- Комментируй код только там, где без комментария не понять.
- Не добавляй зависимости без необходимости.

## Окружение

- ОС: Windows, терминал: Git Bash.

## Самопроверка и самовосстановление

- После запуска долгих задач (конвейеры, волны обработки, очереди, фоновые
  процессы) — проверять их живость и результат по логам/состоянию самому,
  не дожидаясь фидбека пользователя.
- Процесс умер, задание упало или результат не долез — перезапускать и чинить
  самому, переиспользуя уже сделанное (кеш/чекпойнты/resume). Не спрашивать
  «перезапустить?» — перезапускать и отчитываться фактом.
- Ко мне — только решения, которые реально меняют деньги, данные или
  направление работы; рутина восстановления — на агенте.
- Перед работой с инфраструктурой проекта (воркеры, планировщики, службы,
  конвейеры) — сначала git pull и прочитай репо-документацию
  (STATE.md / HANDOFF.md / README): там описано, что запускается
  автоматически и какие копии каноничные. Изменил инфраструктуру —
  сразу отметь в STATE.md.

## Железо и параллелизм

- Продумывая архитектуру любого конвейера/обработки, сначала учитывай железо
  целевой машины: рабочий ПК — i7-14700KF (8P+12E, 28 потоков), 32 ГБ RAM,
  RTX 3050 6 ГБ; homelab — только оркестрация, его CPU под тяжёлое не тратить.
- По умолчанию закладывай параллелизм: CPU-bound — пул процессов на ~половину–2/3
  логических ядер, GPU-bound — батчи/шардирование; однопоточный обход больших
  наборов файлов не писать.
- Для pymupdf/docling/numpy — процессы, а не потоки (GIL и потокобезопасность);
  на Windows не забывать `if __name__ == "__main__":`.
- Долгие/параллельные обработки: инкрементальные чекпойнты (отмена ≠ старт
  с нуля); число воркеров подбирать консервативно (старт 1–2, рост только по
  стабильным замерам под нагрузкой); у фоновых задач — лог с таймстемпами
  и проверка пульса: нет прогресса ~30 минут → убить зависшее, снизить
  параллелизм, перезапустить с чекпойнта (эскалационная лестница — скилл
  planning-with-files).

## Дисциплина завершения работы

- Работаешь в репозитории, где в корне есть `STATE.md` (sync-репозиторий) —
  перед завершением: обнови STATE.md (что сделано, где остановился, что дальше)
  и закоммить изменения. Пушить не обязательно — автосинк доедет сам.

## Разработка кода и игровых/симуляционных сцен

- Без субагентов: генерацию кода, рефакторинг и архитектурное планирование
  выполняет только основной агент в одном непрерывном контексте (субагенты
  не наследуют память проекта → рассинхрон и битая логика).
- Не one-shot: многофайловые проекты не генерировать целиком за раз —
  модуль за модулем, после каждого проверка (запуск, логи, точки входа).
- Самопроверка взаимодействий: клики/биндинги реально меняют состояние
  (KeyW/KeyS → forward/backward без инверсии осей); коллизии, рейкасты,
  невидимые барьеры/рампы проверять до сдачи 3D/canvas-сцены.
- Визуал строго по ТЗ: размеры, цвета, токены — только из спеки, ничего
  не выдумывать. У материалов/шейдеров/геометрии — валидные fallback-цвета
  и геометрия (сцена не должна рендериться чёрной/пустой); камера (target)
  и свет настроены на нормальную видимость.
- Механика: поворот персонажа отделён от орбиты камеры (без укачивания);
  чекпойнты/триггеры валидируются строго по возрастанию, внеочередные
  срабатывания исключены; в симуляциях нет жёстко зашитого перевеса
  одной из сторон.
